# Retro: 2026-11-22 products FK cascade deleted production data

Skill: `retro` (mattpocock-skills). Scope: how migration `20261122_084906_product_weight_grams` destroyed production catalog metadata, and what environment changes would have stopped it. Investigation only — no code or migrations changed.

## Root cause

Changing `weight` from text to number forced a drizzle **table rebuild**: copy → `DROP TABLE` → rename, wrapped in `PRAGMA foreign_keys=OFF/ON`. Payload runs every migration inside a transaction (`initTransaction`/`commitTransaction` in `@payloadcms/drizzle/dist/migrate.js`, verified), and SQLite **silently ignores `PRAGMA foreign_keys` inside a transaction** — no error, no warning. So FKs stayed live and each `DROP TABLE` fired the `ON DELETE` actions defined since the initial migration:

| Table (dropped) | Inbound FK | Action | Result in prod |
|---|---|---|---|
| `products` | `_products_v.parent_id` | SET NULL | every version row orphaned |
| `products` | `products_tags`, `products_characteristics`, `products_gallery` | CASCADE | all rows deleted |
| `_products_v` | `_products_v_version_tags/_characteristics/_gallery` | CASCADE | all snapshot rows deleted |

`products` rows themselves survived (copied before the drop). Admin broke visibly — the product list queries drafts joined on `parent_id`, showing rows with ID null ("The document with ID null could not be found"). Public product pages lost tags, characteristics, and gallery until repair. Orders untouched.

The migration **succeeded** — no SQL error, build passed, deploy shipped. That is the core failure mode: every guard in the pipeline detects migrations that *throw*; this one corrupted silently.

## Why every guard missed

1. **Preview canary existed and was bypassed by workflow, not by code.** `refresh-preview.yml` fires on PR open; the whole weight effort moved via local merges and a direct master push. No PR → no preview refresh → no preview build → the migration's first execution anywhere was the production build.
2. **Even a fired canary only catches migrations that throw.** The canary's signal is a failed build; this migration passes. Catching it on preview required a human diffing/eyeballing preview admin data — the structural guard detects the wrong failure class for silent corruption.
3. **Dev push mode makes migrations write-only artifacts.** ADR 0004: dev diffs-and-pushes schema, so generated migration SQL is never executed locally. Tests cover the guard scripts (`db-baseline`, `migrate-guard` int specs), never a migration against data. Nothing anywhere ran this SQL before prod.
4. **The pre-commit reminder checks presence, not content.** `schema-change-reminder.ts` saw a staged migration and printed "✅ … assuming handled" — a green checkmark that raises confidence without inspecting the SQL.
5. **No CI on master.** The only workflow is `refresh-preview.yml`; lint (`biome` via lefthook) runs locally. Nothing server-side gates a master push.
6. **No standing backup.** Recovery hinged entirely on the dev's instinct to dump prod ~2h before committing. Nothing in `migrate-guard.ts` or the pipeline takes or requires a pre-migration backup.
7. **Generated boilerplate is invisible to review.** Drizzle emits the PRAGMA+rebuild pattern as the standard way to change a column type; the post-review pass (7a881cb) read the migration closely enough to fix comma-decimal parsing in it and still pattern-matched the scaffold as safe.

## Near-misses

- The `down()` of the weight migration carries the same PRAGMA/DROP flaw — a rollback would have re-damaged the rebuilt tables. Never ran (no rollback path is wired anyway), but it sat reviewed and merged.
- Seven earlier migrations were all additive (`ALTER TABLE ADD COLUMN`) — the rebuild path had never fired before, so there was no prior scare to surface the pragma behavior.
- The manual backup was taken *before* the code was even written — one habit, not a system, between this incident and unrecoverable data loss (post-backup saves had to be reconstructed by slug joins).

## Action items (by severity)

1. **Automated check — flag destructive migrations (mechanical, deterministic).** Extend `schema-change-reminder.ts` or add a CI job: any staged/committed migration containing `DROP TABLE` on a table with inbound FKs fails (or hard-warns with exit signal) until split/justified. This turns ADR 0004's prose rule into a check; per the retro skill, mechanical rules get checks, not standards documents.
2. **Automated check — pre-deploy canary on master pushes.** Extend the refresh-preview mechanism (or a `workflow_dispatch`/`push: master` variant) to replay the prod dump and run pending migrations *before* the Vercel prod build migrates, with post-migrate sanity assertions (row counts / orphan checks on FK-referencing tables) so silent corruption fails loudly instead of relying on build errors.
3. **Automated check — standing pre-migration backup.** `migrate-guard.ts` dumps prod Turso before `payload migrate` on every production build, timestamped. Converts the ad-hoc save into structure; makes every future repair possible.
4. **Process — schema changes go through a PR** (CLAUDE.md rule) so the existing canary fires at all. Solo-maintainer convenience pushes of schema-bearing changes are the bypass that mattered.
5. **Information access — post-migrate assertions in `migrate-guard.ts`** (orphan count on `*_v.parent_id`, row-count deltas on array tables) fail the build after a silently corrupting migration.

Not pursued: hardening drizzle's generated output by hand (fights the generator; the ADR split rule plus check #1 is the sustainable seam), and rollback tooling (no atomic need once #1–#3 exist).
