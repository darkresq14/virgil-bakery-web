# ADR 0004: Split dev/prod databases and adopt versioned migrations

## Status

Accepted

## Context

The app runs Payload 3.x on Vercel against a single Turso (libSQL) database shared by local development and production. Schema is kept in sync by Payload's Drizzle `push` mode, which runs whenever `NODE_ENV !== 'production'` — meaning every time a developer boots `pnpm dev` locally (where `.env` points `DATABASE_URL` at prod Turso), the config schema is diffed and pushed **directly into the production database**. There are no migrations (`src/migrations/index.ts` is empty). Dev media uploads share production's Vercel Blob store. SQLite transactions are off (the adapter default).

This has three problems:

1. **Dev mutates prod directly** — schema changes land unversioned, unreviewed, and without rollback the moment a developer starts the local server; test data and accidental edits hit real customer data.
2. **No controlled schema evolution** — there is no migration history, no review gate, and no way to reject a deploy whose schema change fails.
3. **No isolation** — dev and prod share one database and one blob store, so dev experiments risk prod data and prod imagery.

The goal: give development its own isolated database and storage, and replace push-to-prod with versioned, CI-gated migrations on production.

## Decision

Split the environments and put production on migrations.

**Topology.** Local development uses a local SQLite file (`file:./dev.db`) as a push-mode sandbox. Production keeps Turso (libSQL) and switches to Payload migrations. Dev media uploads write to a local `public/media` directory; the Vercel Blob plugin is enabled only in production (`VERCEL_ENV === 'production'`). Dev still renders production images via their public blob URLs.

**Dev data refresh.** A `db:pull` script takes a one-way SQL snapshot of prod Turso (`turso db dump`) and restores it into the local file, giving dev a writable copy of realistic data. This is a snapshot, not a libSQL embedded replica — replicas make the remote the primary and would forward dev writes back to prod, defeating the isolation.

**Prod migrations.** Migrations run at **build time** on Vercel (`payload migrate && next build`), guarded so the migrate step only executes when `VERCEL_ENV === 'production'` (preview builds must not migrate against a non-existent DB). Runtime `prodMigrations` is explicitly rejected — it slows serverless cold starts, which the Payload docs warn against.

**Adopting migrations on the existing prod schema.** The initial migration generated by `payload migrate:create` is a full set of `CREATE TABLE` statements that prod already satisfies, so it cannot be run against prod. Instead the initial migration is **manually baselined**: a single row is inserted into prod's `payload-migrations` table (`{ name, batch: 1 }`) via the Payload local API, marking it applied without executing it. The `db:baseline` script also removes any push-mode `batch = -1` marker rows first — their presence would otherwise trigger an interactive prompt in `payload migrate` that hangs non-interactive (Vercel) builds. Schema match was confirmed by a final push (dev was already running against prod and the schema tree was clean at cutover), not a full schema diff.

**Transactions.** Left off. The only write path (the `Orders` collection) is a single insert followed by a revalidation hook (not a DB write), so nothing today needs multi-write atomicity. Enabling later is a one-line change; revisit when an atomic operation (e.g. order + stock decrement, order + audit log) is added.

## Considered alternatives

- **Second Turso DB for dev (instead of a local file).** Rejected — only worth it if Vercel Preview Deployments need a live backend, which this project does not use. A local file is free, instant, offline, and fully isolated. *(The preview-backend question is revisited in ADR 0005, which adopts a shared preview Turso DB; the dev-file decision here stands.)*
- **Shared prod blob store in dev.** Rejected — once `db:pull` restores prod media rows (which point at prod blob URLs), deleting or replacing a media item in dev would issue a real `DELETE` against prod blobs, destroying live imagery. Local dev storage removes that hazard.
- **Runtime migrations (`prodMigrations`).** Rejected — slows every serverless cold start; the Payload docs warn against it on Vercel.
- **Schema-diff verification of the baseline** (apply the initial migration to a throwaway DB and diff `.schema` against prod). Rejected in favour of a final push, because the schema tree was clean and prod had been push-synced recently; lower rigor accepted given the stable schema.
- **Enable transactions now.** Rejected — no current operation needs it; Turso-over-HTTP transactions add complexity for no present benefit.

## Consequences

### Positive
- Dev is fully isolated — schema experiments, test orders, and accidental edits cannot reach prod.
- Schema changes are versioned, reviewable, and rollbackable; a failing migration rejects the deploy before it ships.
- Local dev is fast, free, and works offline.
- Dev renders realistic prod imagery without touching the blob store.

### Negative
- Schema changes now require a deliberate `migrate:create` → review → commit → deploy loop; the "just boot dev against prod" path is gone.
- Dev data is a stale snapshot, refreshed manually via `db:pull`.
- Two storage code paths to keep in mind (local files vs Vercel Blob).

### Risks
- The manual baseline mark could lie if prod drifts from the config captured in the initial migration — mitigated by verifying the schema tree was clean and confirming the `payload_migrations` row before baselining.
- `db:pull` brings prod `orders` (customer names, phones, addresses) onto the dev laptop. Accepted: the sole developer already has prod admin access. The script can strip/anonymise `orders` if this changes.
